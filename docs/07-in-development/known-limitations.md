# Known Limitations & Gaps to 1.0

This document tracks known architectural limitations, technical debt, and pending optimizations in the current release.

---

## 1. Operating System Background Lifecycles (WP-016)

- **Limitation**: Currently, task workers and outbox replication loops run inside the application runtime.
- **Impact**: On desktop, exiting the application completely terminates replication. On Android, if the operating system kills the application process to reclaim memory, replication pauses until the user re-launches the app.
- **Path to Resolution**: Implement native Android WorkManager bindings and Windows tray background execution.

---

## 2. Release Artifact Signing (WP-018)

- **Limitation**: Windows MSI/NSIS installers and Android APKs generated by CI are unsigned.
- **Impact**: Windows SmartScreen displays an "Unknown Publisher" warning on installation. Android requires developer mode sideloading.
- **Path to Resolution**: Configure Authenticode code signing certificates and Android release keystore secrets in GitHub Actions.

---

## 3. Database Encryption at Rest (R-006)

- **Limitation**: The local SQLite database (`platform.sqlite3`) is stored unencrypted in the user application data directory.
- **Impact**: Anyone with root or physical filesystem access can inspect database records.
- **Mitigation**: Private cryptographic keys and passwords are NEVER stored in SQLite. They are managed in protected native files or memory. Transparent encryption (SQLCipher) is slated for post-1.0.

---

## 4. Large Binary Attachments (R-008)

- **Limitation**: Canonical replication envelopes are optimized for JSON metadata and structured business records under 10MB.
- **Impact**: Syncing large multi-megabyte media files (images, PDFs) directly through canonical JSON envelopes is inefficient.
- **Path to Resolution**: Phase 7 will introduce dedicated content-addressed blob streaming using iroh's native BLAKE3/Bao chunked transfer protocol.

---

## 5. Synchronous Spreadsheet Parsing Budget (CS-013)

- **Limitation**: SheetJS workbook parsing is currently executed synchronously within the webview or worker thread.
- **Impact**: While bounded by size and row limits (10MB / 10,000 rows) with a 5-second timeout check, hard CPU interruption mid-parse requires worker thread isolation.
- **Path to Resolution**: Move large file parsing to a dedicated Web Worker or native Rust parser (`calamine`).

---

## 6. Native Transaction Read Constraint (B-01)

- **Limitation**: `db.transaction()` callbacks use a two-phase IPC model: SQL `execute()` operations are collected during the callback, then dispatched atomically to the Rust `rusqlite` layer in a single IPC call. Calling `txClient.query()` (a read) inside the callback is not supported and will throw a `DatabaseError`.
- **Impact**: Any code that attempts to read data within a `db.transaction()` callback will fail at runtime with a clear error message. All reads must be performed **before** entering the transaction boundary.
- **Correct pattern**:
  ```typescript
  // ✅ Read first, then write in transaction
  const existing = await db.query<Row>("SELECT * FROM widgets WHERE id = ?", [id]);
  if (existing.length === 0) throw new Error("Not found");

  await db.transaction(async (tx) => {
    await tx.execute("UPDATE widgets SET name = ? WHERE id = ?", [name, id]);
    await tx.execute("INSERT INTO core_audit_log ...", [...]);
  });
  ```
- **Path to Resolution**: If a read-then-write sequence must be strictly atomic (to prevent race conditions), create a dedicated Rust Tauri command that executes the full read-then-write sequence inside a single `rusqlite` transaction on the Rust side.
